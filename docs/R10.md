# R10: life presentation and safe termination (partial)

Status: deterministic planning layer only — meaning, presentation, safe-stop rules, candidate planning, and WORLD's logical activity mapping. R10 movement, occupancy, Activity selection, and measured spatial behavior are not implemented. This document records the boundary so the partial layer is not mistaken for a playable R10.

## Implemented

- `internal/life.Assess` maps fresh/expired/empty/missing WorkSet and LifePolicy heads to explicit states.
- `WorkPresentation` distinguishes queued, waiting, remote, and presence-required running work. Only the presence-required case may ask a later controller to plan movement.
- Multiple running work items still produce one presentation decision; presence-required work dominates and no per-task body/movement controller is introduced.
- `PlanStop` requires an explicit interruption rule, plans bounded cleanup, and keeps physical occupancy held unless the rule explicitly releases it.
- `DefaultActivityDefinitions` is WORLD's owner mapping of the eight registered non-cognitive IDs onto their logical posture, motion, and occupancy meaning, with the interruption rule each activity needs to be stoppable:

| Activity | Logical occupancy | Relocates the Actor | Safe interruption |
|---|---|---|---|
| `change_clothes` | `private_room` | yes | stop standing, room stays held |
| `exercise` | `exercise_mat` | yes | stop standing |
| `idle` | none | no | stop standing; the only candidate while presence-required work runs |
| `read` | `study_seat` | yes | stop standing |
| `rest` | `sofa` | yes | stop sitting |
| `sit` | `chair` | yes | stop standing |
| `sleep` | `bed` | yes | none; a lost permission holds the Actor in bed instead of moving it |
| `walk` | `path` | yes | stop standing |

  Every entry defines a stop state, so every entry is publishable as a candidate, and `ReleaseOccupancy` is `false` for all of them: D-11 forbids releasing a physical resource while the body may still be on it, and WORLD has no measured movement or occupancy route, so no activity may grant a release or a cleanup step yet. Occupancy names are logical only — not anchor IDs, room graph nodes, coordinates, or reservations — and `DefaultActivityDefinitions` returns copies so a controller cannot mutate the owner mapping.
- The provisional R09 assessment route exposes the meaning/presentation result for a bound CORE Actor and publishes this mapping as `executable_activity_ids`; it is read-only, selects nothing, starts nothing, and claims no place, reservation, or measured geometry (D-17/D-18 stay open).
- The route publishes the D-13 task ID lists — `queued_task_ids`, `waiting_task_ids`, `running_task_ids`, `presence_task_ids` — so a consumer can see why the Actor stays in place: queued work alone never implies movement and waiting/blocked work starts no new work. Normal Chat never reaches WORLD because the projection contract admits `assigned_work` only.
- The same provisional route publishes the stop-planning decision for one activity the caller names (`stop_planning_activity_id`, documented in [R09](R09.md)). The caller sends only the activity ID; the posture, logical occupancy, and interruption rule come from the owner mapping above, an ID outside that mapping is rejected, and a `hold` decision grants no posture and no action. Publishing a decision stops, starts, and moves nothing and writes no WORLD State.
- A WORLD interruption/stop plan does not cancel, fail, or complete CORE work.
- Projection evaluation creates no WORLD Event, State change, or Command Receipt.
- `ExecuteContinuation`, `ReleaseOccupancy`, and `ExecuteAdmission` in `internal/life` execute the planning decisions against a logical ledger (activity, logical occupancy name, posture, receipt log) only. A stop runs only the owner-authorized actions and applies the posture from the activity's own interruption rule; it never releases occupancy and never changes `Position`. Release is a separate capability authorized only after the stop action executed. A start begins exactly one admitted candidate on an idle ledger, refuses refused or mismatched candidates, movement-requiring starts, and held-occupancy overwrite; every refusal mutates nothing. No route, Event, or WORLD State wiring consumes this yet.
- `HandleActivityStart`, `HandleActivityStop`, and `HandleOccupancyRelease` in `internal/life` are the Event/Receipt rules for presentation start, interruption, and safe stop (D-11). They are registered `store.Handler`s on the canonical Command → Handler → Receipt route: one action commits one Event and one State transition.

  | Action | Committed Event | State projection effect |
  |---|---|---|
  | `life.activity.start` | `life.activity.started` | the Actor points at the activity, which becomes `running` |
  | `life.activity.stop` | `life.activity.stopped` — the rule's stop state, the owner-authorized actions, and the still-held logical occupancy | the activity becomes `stopped` and the Actor's activity pointer clears; the room is untouched |
  | `life.occupancy.release` | `life.occupancy.released` — the logical occupancy name that stopped being held | the activity becomes `released` |

  A payload carries `actor_id` and `activity_id` only, and strict decoding rejects anything else: posture, occupancy, and cleanup come from the owner mapping above, so a caller cannot choose a State delta. A start commits only for an Actor that runs nothing, a registered activity, and an occupancy that already equals the Actor's canonical room — a start that would relocate the Actor is refused, because WORLD performs no movement (D-17). A stop runs only through the activity's own interruption rule and never releases occupancy, and `sleep` defines no rule, so stopping a sleeping Actor is refused and holds the Actor in bed. Release is a separate capability that requires a committed stop and refuses when the activity held nothing. Cancelling an activity and releasing what a body may still be on are never one operation.
  Every refusal is a `rejected` Receipt with no transaction, no Event, and no State change, and the same idempotency key and body replays the same Receipt — including a rejected one — without a second effect. No Event in this table describes CORE work: a WORLD stop is a life event and never cancels, fails, or completes a CORE task.
  `internal/life/commands_test.go` proves the table against the real SQLite EventStore. The reservation primitives stay unused because the binding between an activity and a real resource, quantity, and reservation identity is item 2, and no production route registers these actions yet — that boundary is documented here and not enforced by a lint or architecture test.

## Not implemented

- No runtime route registers the lifecycle actions above, so no running WORLD applies the controller logic or the Event rules to WORLD State or a real Actor. The controller executes the logical ledger only, nothing selects candidates on its own, and `Assess` still takes the catalog from its caller.
- No measured occupancy metadata. The mapping above states a logical name per activity; the resource, its quantity, and its reservation identity stay unbound, so admitting an activity claims no place exists or is reachable.
- Path planning, room graph, measured coordinates, doors, stairs, furniture occupancy, and reservations.
- Starting/ending movement or changing `ActorState` from a presentation decision.
- Viewer-facing presentation, WorkPresentation events, and privacy filtering.
- Executing a stop plan beyond the logical ledger and the rule handlers above: no runtime route registers those actions, so a published decision reaches no WORLD State and no real Actor, and the assessment route stays provisional with no adopted CORE contract.
- CORE work-result Receipt integration and duplicate external work prevention.

## Required before R10 completion

1. Geometry PoC artifact and `spatial_ready` evidence (R03/R11/R14).
2. Bind each activity to a real resource and reservation, and decide whether it may release occupancy on stop. That needs the measured evidence in item 1, not a local guess.
3. A single life controller that owns all movement and occupancy for one Actor.
4. Event/Receipt rules for presentation start, interruption, and safe stop. The rules, their Events, and their Receipt behaviour exist on the canonical store route (D-11); registering them on a runtime route and proving them against a real Actor stays open with items 3 and 5.
5. Real CORE Outbox E2E through the canonical route.
6. macOS and multi-OS behavior evidence.

Until then, the implemented code is a testable meaning/presentation foundation, not a finished life simulator.
