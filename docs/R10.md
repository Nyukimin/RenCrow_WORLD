# R10: life presentation, safe termination, and home controller (partial)

Status: WORLD now has a canonical home command controller backed by the R06 EventStore, plus the earlier deterministic planning layer. The controller loads only with an operator-supplied strict versioned home layout; authenticated HTTP home commands additionally require a separate `life` credential bound to exact Actor IDs. It does not promote `spatial_ready`, imply a production deployment, or establish CORE diary acceptance. The checked HOUSE example is in [`examples/house-105/home-layout.json`](../examples/house-105/home-layout.json); its `scene_sha256` identifies the source scene.

## Implemented

- `internal/life.Assess` maps fresh/expired/empty/missing WorkSet and LifePolicy heads to explicit states.
- `WorkPresentation` distinguishes queued, waiting, remote, and presence-required running work. Only the presence-required case may ask a later controller to plan movement.
- Multiple running work items still produce one presentation decision; presence-required work dominates and no per-task body/movement controller is introduced.
- `PlanStop` requires an explicit interruption rule, plans bounded cleanup, and keeps physical occupancy held unless the rule explicitly releases it.
- `DefaultActivityDefinitions` is WORLD's owner mapping of the eight registered non-cognitive IDs onto their logical posture, motion, and occupancy meaning, with the interruption rule each activity needs to be stoppable:

| Activity | Logical occupancy | Relocates the Actor | Safe interruption |
|---|---|---|---|
| `change_clothes` | `private_room` | yes | stop standing, room stays held |
| `exercise` | `exercise_mat` | yes | stop standing |
| `idle` | none | no | stop standing; the only candidate while presence-required work runs |
| `read` | `study_seat` | yes | stop standing |
| `rest` | `sofa` | yes | stop sitting |
| `sit` | `chair` | yes | stop standing |
| `sleep` | `bed` | yes | none; a lost permission holds the Actor in bed instead of moving it |
| `walk` | `path` | yes | stop standing |

  Every entry defines a stop state, so every entry is publishable as a candidate, and `ReleaseOccupancy` is `false` for all of them: D-11 forbids releasing a physical resource while the body may still be on it, and WORLD has no measured movement or occupancy route, so no activity may grant a release or a cleanup step yet. Occupancy names are logical only — not anchor IDs, room graph nodes, coordinates, or reservations — and `DefaultActivityDefinitions` returns copies so a controller cannot mutate the owner mapping.
- The provisional R09 assessment route exposes the meaning/presentation result for a bound CORE Actor and publishes this mapping as `executable_activity_ids`; it is read-only, selects nothing, starts nothing, and claims no place, reservation, or measured geometry (D-17/D-18 stay open).
- The route publishes the D-13 task ID lists — `queued_task_ids`, `waiting_task_ids`, `running_task_ids`, `presence_task_ids` — so a consumer can see why the Actor stays in place: queued work alone never implies movement and waiting/blocked work starts no new work. Normal Chat never reaches WORLD because the projection contract admits `assigned_work` only.
- The same provisional route publishes the stop-planning decision for one activity the caller names (`stop_planning_activity_id`, documented in [R09](R09.md)). The caller sends only the activity ID; the posture, logical occupancy, and interruption rule come from the owner mapping above, an ID outside that mapping is rejected, and a `hold` decision grants no posture and no action. Publishing a decision stops, starts, and moves nothing and writes no WORLD State.
- A WORLD interruption/stop plan does not cancel, fail, or complete CORE work.
- Projection evaluation creates no WORLD Event, State change, or Command Receipt.
- `ExecuteContinuation`, `ReleaseOccupancy`, and `ExecuteAdmission` in `internal/life` execute the planning decisions against a logical ledger (activity, logical occupancy name, posture, receipt log) only. A stop runs only the owner-authorized actions and applies the posture from the activity's own interruption rule; it never releases occupancy and never changes `Position`. Release is a separate capability authorized only after the stop action executed. A start begins exactly one admitted candidate on an idle ledger, refuses refused or mismatched candidates, movement-requiring starts, and held-occupancy overwrite; every refusal mutates nothing. No route, Event, or WORLD State wiring consumes this yet.
- `SelectCandidate` connects that owner mapping to the controller (D-28): it returns the one activity the controller may start now, in activity-ID order, taken from the owner table rather than a caller-supplied definition, together with a copy of that owner definition. It selects at most one candidate, mutates nothing, and never selects an activity whose start would move the Actor — that would plan a move no controller can execute and read as a claim that a place exists or is reachable (D-17/D-18). `idle` is the only registered activity that relocates nothing, so a permission holding only moving activities selects nothing and returns `ErrNoCandidate` naming the WORLD reason. `ExecutableActivityIDs` still publishes the wider candidate set for the later controller that owns movement, and no route or real Actor consumes the selection yet. `internal/life/registration_architecture_test.go` enforces that boundary: a production file outside `internal/life/` that calls `SelectCandidate` fails until an allowlist entry names the R10 items it closed.
- `HandleActivityStart`, `HandleActivityStop`, and `HandleOccupancyRelease` in `internal/life` are the Event/Receipt rules for presentation start, interruption, and safe stop (D-11). They are registered `store.Handler`s on the canonical Command → Handler → Receipt route: one action commits one Event and one State transition.

  | Action | Committed Event | State projection effect |
  |---|---|---|
  | `life.activity.start` | `life.activity.started` | the Actor points at the activity, which becomes `running` |
  | `life.activity.stop` | `life.activity.stopped` — the rule's stop state, the owner-authorized actions, and the still-held logical occupancy | the activity becomes `stopped` and the Actor's activity pointer clears; the room is untouched |
  | `life.occupancy.release` | `life.occupancy.released` — the logical occupancy name that stopped being held | the activity becomes `released` |

  A payload carries `actor_id` and `activity_id` only, and strict decoding rejects anything else: posture, occupancy, and cleanup come from the owner mapping above, so a caller cannot choose a State delta. A start commits only for an Actor that runs nothing, a registered activity, and an occupancy that already equals the Actor's canonical room — a start that would relocate the Actor is refused, because WORLD performs no movement (D-17). A stop runs only through the activity's own interruption rule and never releases occupancy, and `sleep` defines no rule, so stopping a sleeping Actor is refused and holds the Actor in bed. Release is a separate capability that requires a committed stop and refuses when the activity held nothing. Cancelling an activity and releasing what a body may still be on are never one operation.
  Every refusal is a `rejected` Receipt with no transaction, no Event, and no State change, and the same idempotency key and body replays the same Receipt — including a rejected one — without a second effect. No Event in this table describes CORE work: a WORLD stop is a life event and never cancels, fails, or completes a CORE task.
  `internal/life/commands_test.go` proves the table against the real SQLite EventStore. The reservation primitives stay unused because the binding between an activity and a real resource, quantity, and reservation identity is item 2, and no production route registers these actions yet. `internal/life/registration_architecture_test.go` enforces that: no production file outside `internal/life/commands.go` may name `life.activity.start`, `life.activity.stop`, or `life.occupancy.release`, and wiring one needs an allowlist entry naming the R10 items it closed (items 3 and 5) and the real-Actor evidence they require.
- The optional `home_layout_path` input is a separate strict `world.home-layout/v1` JSON document. It names `scene_sha256`, room anchors `[x,y,z]`, directed measured paths and durations, Actor-to-private-room mappings, measured in-room furniture slots, and an optional per-Actor mirror repertoire. Unknown or duplicate JSON keys, unknown rooms, duplicate private-room ownership, non-finite coordinates, and invalid slot/path geometry are rejected. `examples/house-105/home-layout.json` records 16 rooms, 30 directed paths, 10 slots, eight Kuro poses, and the source scene digest `602a80fee5ce300ecfd3bee8cb4b316f4b3c95a6fda207a14cc95e06aaac840e`.
- When that layout is configured, the canonical authenticated `POST /v1/worlds/{world}/timelines/{timeline}/commands` path registers only the closed `life.home.*` vocabulary. A `life` token must carry an exact non-empty `life_actor_ids` list and cannot also carry `write`; existing `write` credentials and standard actions stay on their existing path. Every accepted command is durably committed as one Store transaction with ordered Events and a Receipt; `Idempotency-Key` replays the same Receipt, while reusing it with another body conflicts.

  | Action | Payload | Committed Event | Effect |
  |---|---|---|---|
  | `life.home.move` | `actor_id`, `room_id`, optional `slot_id` | `life.home.move.started` | Reserves measured directed corridors and an optional target slot; keeps the last confirmed room and position while the route is active. |
  | `life.home.finish` for a move | exact `actor_id`, active `activity_id` | `life.home.move.arrived` | Allowed after the server-calculated due time and only while the persisted route still matches its pinned layout; updates room, position, and slot, then releases reservations. |
  | `life.home.sleep` | `actor_id` | `life.home.sleep.started` | Requires the Actor at its configured bed slot and reserves it until the exact sleep instance is woken. |
  | `life.home.wake` | exact `actor_id`, active sleep `activity_id` | `life.home.sleep.woke` | Ends sleep using server time and releases its bed reservation. Generic stop and finish cannot end sleep. |
  | `life.home.exercise` | `actor_id` | `life.home.exercise.started` | Requires the Actor at its configured exercise anchor and holds that slot for its configured duration. |
  | `life.home.mirror_pose` | `actor_id`, configured `pose_id` | `life.home.mirror_pose.started` | Requires Kuro's configured mirror slot and a pose in the operator-authorized repertoire. |
  | `life.home.finish` for exercise or a pose | exact `actor_id`, active `activity_id` | `life.home.exercise.completed` or `life.home.mirror_pose.completed` | Allowed after the server-calculated due time; completion is counted only on the committed mirror completion. |
  | `life.home.stop` | exact `actor_id`, active non-sleep `activity_id` | `life.home.activity.stopped` | Stops movement, exercise, or a mirror pose and releases its reservations without fabricating arrival. |

  Activity IDs identify one persisted instance rather than an activity kind. Start/due/end timestamps and elapsed duration come from the server clock. Snapshot adds optional `activity_kind`, `pose_id`, `activity_started_at`, `activity_due_at`, `position`, `slot_id`, and move target/route fields. The top-level optional `home_scene_sha256` and `home_move_points` are read projections; path points are returned only for an active route whose stored layout hash still matches. Those projections do not enter the persisted `state_hash`. Layout reload prevents an old move from arriving, while the exact persisted resource IDs still allow a safe stop. The old `life.activity.*` route is not activated alongside this controller; R05 remains unchanged, and zero-value additions to the old state shape are omitted.
- `internal/life/home_test.go` covers strict layout validation, actual directed route resolution, private-room ownership and transit, corridor and slot reservation, server-timed finish/wake/stop, Kuro's configured poses and unique completion count, and layout-reload recovery. `internal/httpapi/home_auth_test.go` covers the canonical authenticated route, separate life/write credentials, exact Actor authorization, stable idempotent Receipts, snapshot projections, and safe stop after an operator layout change. The HOUSE example test pins its source digest and checks that each configured private room can be reached from and exited to the shared living room.

## Not implemented

- The `life.home.*` actions are an explicit command surface, not an autonomous routine. No CORE Outbox-to-WORLD end-to-end or durable CORE diary readback is claimed by these isolated WORLD tests.
- The checked HOUSE layout has source-scene and route evidence, but production browser collision verification and deployed listener acceptance remain open; `/health/ready` continues to report `spatial_ready:false` until the separate readiness evidence is accepted.
- The earlier planning layer still does not select or start an activity automatically: `Assess` takes its catalog from the caller, and no running routine consumes `SelectCandidate`.
- Viewer-facing presentation, WorkPresentation events, and privacy filtering.
- Wiring the earlier logical `life.activity.*` and occupancy lifecycle rules alongside home actions. Home actions currently own one activity per Actor; the planning ledger remains isolated to avoid a second owner.
- CORE work-result Receipt integration, duplicate external work prevention, and adopted cross-module read/diary contract.

## Required before R10 completion

1. Complete production browser collision verification and record accepted `spatial_ready` evidence (R03/R11/R14).
2. Complete isolated production-listener acceptance with the authorized layout and credentials.
3. Complete real CORE Outbox E2E through the canonical route, then verify the durable CORE diary from the resulting WORLD Events/Receipt.
4. Define the adopted cross-module snapshot/privacy contract and the Viewer-facing presentation projection.
5. Complete macOS and multi-OS behavior evidence.

Until those acceptance items are closed, the controller remains a source implementation with a checked operator layout, not a production-accepted life simulator.
