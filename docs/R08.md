# R08: CORE projection inbox source foundation

Status: WORLD-side R08 input foundation. It accepts and durably orders full CORE-owned WorkSet v2 and LifePolicy projections. Linux and Windows 11 amd64 source tests plus R08 E2E (real binary, real SQLite file, auth, restart, epoch reconciliation) pass; macOS is unverified. CORE has not adopted the projection permission, publisher, or payload contracts, and no canonical WORLD route/port is claimed.

This unit does **not** implement R09 activity behavior, R10 LifeController choices, expiry-driven fallback, WorkPresentation, or a real CORE Outbox. It is the ordered, durable inbox those units must consume.

## What is implemented

`internal/projection` validates the provisional envelope and the reference payload schemas:

- exact `world_id`, `timeline_id`, `timeline_epoch` destination;
- `CoreProjectionEnvelope` (`world.contracts/v1`) with one of `full_actor_work_set` or `life_policy`;
- full WorkSet v2 (`rencrow.world.work-set/v2`): `queued`/`waiting`/`blocked` may omit `run_id`; `running` requires one; terminal states and unknown fields are rejected;
- LifePolicy (`world.life-policy/v1`): required persona/condition references, bounded unique activity IDs, UTC expiry;
- duplicate JSON keys, trailing JSON, non-object payloads, invalid UTF-8, and oversized envelopes;
- SHA-256 over deterministic JSON (sorted object keys, integer numbers) as the canonical payload digest.

`internal/store/projection.go` provides the durable inbox:

- operator-authorized `ActorID -> ActorInstanceID` binding per World/Timeline;
- ordering and idempotency scoped by destination, Actor binding, projection kind, and source epoch;
- same epoch/revision/digest is `duplicate`; same revision with another digest is `revision_conflict`; an older revision is `stale_revision`;
- a new `source_epoch` requires `ReconcileProjection`; after reconciliation every later projection from the retired epoch is `epoch_superseded`;
- heads, retired epochs, acknowledgements, and reconciliation records are committed in one SQLite transaction and survive restart;
- projections never create a WORLD Event, State change, Command Receipt, or Command idempotency row.

`internal/httpapi` exposes the provisional target route:

```text
PUT /v1/worlds/{world}/timelines/{timeline}/core-projections/{actor}/{kind}
```

The body is one `CoreProjectionEnvelope`. `{kind}` is `full_actor_work_set` or `life_policy` and must match the envelope. `{actor}` is the ASCII transport ID from [ID.md](ID.md); it must match `payload.actor_id`. Add `?reconcile=true` only for an authenticated epoch switch with a fresh full projection.

The route requires the `projection` token scope. A read/write/stream token cannot publish projections, and a projection token cannot append Commands. Transport errors use the normal error body; ordering outcomes use a separate projection acknowledgement:

```json
{
  "schema_version": 1,
  "projection": {
    "ack_id": "prj_...",
    "status": "accepted",
    "projection_kind": "full_actor_work_set",
    "source_epoch": "core-epoch-1",
    "source_revision": 10,
    "digest": "...",
    "accepted_at": "2026-10-20T02:03:04Z",
    "recorded_at": "2026-10-20T02:03:04Z"
  }
}
```

`duplicate` is `200`; `stale_revision`, `revision_conflict`, `epoch_requires_reconcile`, `epoch_superseded`, and `epoch_unchanged` are `409`. Invalid envelopes/payloads are `400`; an unbound Actor or wrong instance is `403`; an oversized body is `413`.

## Configuration

Add the projection credential and the explicit Actor binding:

```json
{
  "tokens": [
    {"id": "core", "sha256": "<64 hex characters>", "scopes": ["projection"]}
  ],
  "core_projection_actors": [
    {"actor_id": "mio", "actor_instance_id": "core-instance-mio"}
  ]
}
```

The binding is operator configuration, not payload data. A projection cannot create or change it. Bindings are scoped to World/Timeline rather than epoch, so a verified restore into a new Timeline epoch keeps the authorized mapping while all projection heads remain epoch-scoped.

## Ordering rules

| Input | Result |
|---|---|
| no head, first full projection | `accepted` |
| same epoch, revision greater than head | `accepted` |
| same epoch, revision less than head | `stale_revision` |
| same epoch/revision, same canonical digest | `duplicate`, no effect |
| same epoch/revision, different digest | `revision_conflict` |
| different epoch, no reconciliation | `epoch_requires_reconcile` |
| `?reconcile=true`, different epoch, full projection | `accepted`; old epoch retired |
| old epoch after reconciliation | `epoch_superseded` |
| `?reconcile=true`, same epoch | `epoch_unchanged` |

`source_epoch` is opaque. The inbox never compares it lexically or numerically with another epoch, `event_seq`, or `state_seq`. `source_revision` is never compared with a WORLD sequence.

## Gaps

- CORE has not adopted `CoreProjectionEnvelope`, WorkSet v2/LifePolicy ownership, projection permission, or projection receipt semantics. This is a WORLD source foundation aligned to the v1.4 reference, not a cross-module contract.
- No canonical WORLD port/route. The HTTP path is provisional.
- No CORE publisher principal identity is stored in the acknowledgement; only the authenticated token scope is enforced. Publisher/outbox identity remains CORE-owned.
- No acknowledgement read route, audit export, retention policy, or operator CLI.
- Expiry, stale WorkSet handling, empty-Set meaning, WorkPresentation, and activity selection are R09/R10 behavior; this inbox only stores the accepted head.
- The R06 restored-epoch Command gate still requires `CompleteReconcile`. Projection reconciliation does not silently open Commands.
- No macOS evidence and no real CORE E2E. Acceptance AC-004/005/012/013 remain `not_run` because they require the real CORE Outbox/issuer and full runtime evidence.
