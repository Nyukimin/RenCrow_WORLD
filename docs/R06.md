# R06: durable EventStore foundation

Status: R06 source implementation of the EventStore foundation. Linux and Windows behavior is verified by `go test ./...` (including real-process crash injection and backup/restore), macOS behavior is unverified, and CORE projections, production handlers, operational backup scheduling, and live acceptance remain unimplemented or unverified. R07 adds an explicit-config HTTP source foundation; its route/port is not adopted. The W14 acceptance matrix entries stay `not_run`; this document records source-level coverage only.

## Scope

`internal/store` is a Go library with one logical writer over SQLite WAL. It is not a running service and has no listener, route, port, credential, LLM, Tool, or network call. R05 `rencrow-world inspect` remains unchanged and does not use the Store.

The Store owns:

- an authoritative Event log scoped by `world_id`, `timeline_id`, `timeline_epoch`;
- one immutable State projection per committed transaction, with a canonical SHA-256 hash;
- a Receipt per Command, including rejected Commands;
- resource capacity, consumption, and per-actor/per-activity reservations;
- Snapshot and per-transaction State deltas for deterministic replay;
- isolated `VACUUM INTO` backups with a verified manifest, restore-to-new-epoch, and `recovery_gap` records.

Handlers are registered typed Go functions (`Store.Register`). They receive the current State and a JSON payload and return the next State, Events, and reservation changes. They never receive a clock, random source, network, LLM, or database handle. R06 ships no production handler set; R10/R11 own activity and spatial rules.

## Transaction commitment

`Append(Command)` opens one SQLite transaction and, in order:

1. resolves the idempotency namespace (`world_id + timeline_id + timeline_epoch + client_id + idempotency_key`) and compares the canonical body digest (SHA-256 over action, canonical payload, and `expected_state_seq`);
2. loads the timeline State at `state_seq` and checks the epoch gate (`superseded_by`, `reconciled`);
3. checks strict CAS when `expected_state_seq` is present;
4. runs the registered handler and applies reservations/consumption;
5. writes Events `state_seq+1 … state_seq+N` under one `txn_id`, updates State and its hash, writes reservation/resource rows, and writes the Receipt;
6. commits once.

A crash before commit rolls back all six steps. The Event log is authoritative; the State row is a projection. A committed Receipt names its `txn_id` and Event IDs. A rejected Receipt (`epoch_superseded`, `epoch_not_reconciled`, CAS mismatch, resource conflict, reservation mismatch, invalid reservation, unknown action, handler error) has no `txn_id` or Event references and changes no State. Malformed commands, unknown action scope, and limit violations return a Go error and write no Receipt.

Limits: at most 128 Events and 256 KiB of serialized Event kind/payload per transaction; the input payload is also capped at 256 KiB. Event pages are capped at 500 Events and 2 MiB by default and never split a transaction; `Page` returns whole transactions and a cursor at the last returned transaction boundary.

Replay uses the latest Snapshot at or before the requested sequence plus the saved per-transaction State deltas. It never reruns a handler, LLM, Tool, or current rule, and it does not read wall-clock time, so the canonical hash is independent of when replay runs. A newly created `timeline_epoch` starts at `event_seq = 0`; a restored epoch resumes at the verified backup boundary. Every epoch is isolated by the scope triple.

## Schema

Tables (all scoped by the triple above):

| Table | Purpose |
|---|---|
| `timeline` | current `event_seq`, `state_seq`, canonical State JSON/hash, `reconciled`, `superseded_by` |
| `snapshot` | initial/checkpoint State at a sequence |
| `txn` | transaction id, contiguous first/last sequence, receipt id, State delta, hash |
| `event` | ordered Events, kind, payload, explicit `recorded_at` |
| `receipt` | idempotency key/digest, committed/rejected status, txn/Event refs |
| `resource` | capacity and consumed quantity |
| `reservation` | resource, actor, activity, quantity |
| `recovery_gap` | omitted sequence interval and reason |
| `epoch_reconcile` | explicit CORE full-resync completion |

SQLite is opened with WAL, `synchronous=FULL`, `busy_timeout`, foreign keys, and `_txlock=immediate`; the connection pool is limited to one connection so Commands serialize as a single logical writer. The driver is `modernc.org/sqlite` v1.60.1 (pure Go, no cgo), chosen so the same source builds on Linux, Windows, and macOS without a C toolchain. Linux and Windows have executed the store tests; macOS has not.

## Backup, restore, and epoch gate

A live database file copy is not a backup. `Backup` uses SQLite `VACUUM INTO` to create a standalone, consistent file, hashes the exact bytes, writes `backup.db.manifest.json` atomically, and re-verifies the result before returning. The manifest records the scope, `event_seq`, `state_seq`, canonical `state_hash`, file SHA-256/size, creation time, and an optional caller `SourceRevision`. `VerifyBackup` checks the manifest, file size/hash, `PRAGMA integrity_check`, and the Timeline row.

`Restore` accepts only a verified backup whose scope exactly equals `OldScope`. In one transaction it:

1. creates `NewEpoch` with the backup State and sequence (`state_seq = event_seq = backup state_seq`);
2. writes a Snapshot at that boundary and restores resource/reservation rows;
3. marks `OldScope` as superseded, so new Commands there are rejected with `epoch_superseded` and have no State effect;
4. records `recovery_gap` for the omitted interval between the backup sequence and the old epoch's last state sequence;
5. leaves `NewEpoch` closed for new Commands (`reconciled = 0`) until a reconcile gate succeeds.

`CompleteReconcileChecked(scope, source_revision, required, at)` is the current explicit CORE full-resync gate. It rechecks every required Actor/kind projection head in one transaction, rejects missing, unbound, wrong-instance, or already-expired heads, records `epoch_reconcile` plus `epoch_reconcile_projection`, and only then sets `reconciled = 1`. The older `CompleteReconcile` remains for R06 compatibility but does not inspect projections and must not be used as the external restore-open operation. Before it succeeds, Commands return a rejected Receipt with `epoch_not_reconciled`. Reads and receipt lookup remain available. Old Receipts and idempotency keys are scoped by `timeline_epoch`, so an old Receipt is never treated as a result in the new epoch.

The restore API has no CLI or HTTP route yet. `rencrow-world serve` continues to serve exactly one configured epoch; after a restore, the operator must point the config at the new epoch, and CORE must call the reconcile gate before new writes.

## Acceptance mapping and gaps

Source-level coverage exists for W14-AC-002 (atomic commit and crash injection), AC-003 (idempotent retry/body mismatch), AC-007 (strict CAS), AC-010 (replay hash and no wall-clock dependence), and AC-015 (transaction-preserving pages and limits). AC-008 is covered only at the reservation primitive level; the Activity lifecycle is a test fixture and belongs to R10/R11.

Not covered: the adopted HTTP contract and canonical route/port (R07 has a provisional source foundation), CORE WorkSet/LifePolicy projections (R08/R09), production activity/space rules (R10/R11), PORTAL read projections, backup/restore CLI/HTTP exposure and scheduling, restore into a fresh Store without an existing old epoch, bounded catch-up beyond the recorded `recovery_gap`, CORE reconcile evidence/Receipt, UTF-8 transport-ID mapping, macOS behavior, and live/E2E acceptance through CORE. The acceptance matrix remains `not_run` until those scenarios are executed with owner evidence.
